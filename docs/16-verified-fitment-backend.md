# Verified bounded fitment backend (PR 4B-B)

## Scope and release limitation

This backend records reviewed, bounded base-vehicle coverage for each immutable offer revision. It does not decode a VIN, assess engines or trims, verify real supplier catalogues, reserve a service, or promise a price for an unlisted variant. Both supported modes require provider-backed evidence that every variant in each listed make/model/year range has the same exact fixed scope, parts, and price. Evidence is an opaque internal reference; a real company-controlled repository and Operations review remain release prerequisites. Synthetic test fixtures are not provider evidence.

Publication remains default-off. Legacy approved revisions retain unassessed fitment and are hidden by public discovery; no universal fitment is backfilled. Existing published legacy rows can be unpublished by Operations. A successor revision copies coverage into an unapproved draft, resets fitment attestations, and needs submission, distinct Operations approval, and explicit publication replacement.

## Lifecycle and HTTP boundaries

- Sales enters draft offer coverage with `PUT /api/v1/staff/offers/{offerId}/revisions/{revisionId}/fitment`. Body: `commandId`, `expectedVersion`, `mode`, `evidenceRef`, and 1–50 `{makeId,modelId,yearFrom,yearTo}` rows. GET at the same path returns draft/review data to authorized staff; Sales may read only its own revision. `GET .../fitment/commands/{commandId}` resolves an actor-bound committed receipt after an unknown response. A changed payload under the same key is a conflict.
- Submission freezes offer and coverage content. A distinct Operations checker must explicitly attest all-variant fitment and fixed scope/price at commercial revision approval. Approval does not publish.
- Sales creates, optionally edits, and submits a category-scoped branch capability version under `/api/v1/staff/branches/{branchId}/fitment-policies`. A distinct Operations checker approves/rejects it. Approval atomically switches the branch/category current pointer; a former active version becomes withdrawn. Operations can withdraw the active version without fallthrough. The command receipt route is `/api/v1/staff/branches/{branchId}/fitment-policies/commands/{commandId}`.
- `GET /api/v1/offers/{offerId}/fitment` exposes only currently effective public make/model labels and inclusive intersected years. `GET /api/v1/garage/{vehicleId}/offer-matches/{offerId}` requires a live verified customer session and owner-scoped stored vehicle. Hidden offer and foreign/missing/archived vehicle are indistinguishable 404. A visible offer returns `MATCH`, `NO_MATCH`, or `UNKNOWN`, the pinned revision, vehicle version, and active capability identity. No `canBook` is emitted.

All mutation endpoints require an allowed Origin/Referer, bounded JSON, role permission and server-side session resolution. Evidence references and staff identity are never in public DTOs. Public/private responses are no-store. The two public reads use one SQL statement each for visibility, pin, active capability, catalog state, and coverage; an already-rendered browser page cannot be recalled after a withdrawal.

## Invariants and operations

The offer revision pin fixes offer-side coverage. Current branch capability can only narrow it. Draft coverage rows are limited and non-overlapping per model, and the database rejects child INSERT/UPDATE/DELETE after submission even through direct SQL. Capability rows similarly freeze after submission. Reviewed versions are immutable and terminal; corrections require a new version. The PostgreSQL migration is additive and does not rewrite historical offers, users, garage vehicles, publications, or receipts.

Provider or branch pause, service/category or vehicle-catalog deactivation, expiry, and capability withdrawal affect the next public read without mutating approved evidence. Operations should withdraw a bad capability immediately and unpublish an affected offer when appropriate; correction is a new Sales draft plus distinct review, followed by explicit replacement. For a lost mutation response, query the same actor's receipt with the original command ID, then retry the exact same intent if no receipt exists. Do not invent a new command after an ambiguous timeout. Transaction failure leaves no partial domain/receipt/audit writes; application errors are sanitized. PostgreSQL server logs require separately restricted operational access and retention.

Lock order: offer mutations acquire provider, branch, offer, revision, then canonical make/model (sorted), service, category and publication. Capability mutations acquire provider and branch, then canonical make/model for draft writes, category, version and pointer. Garage mutations retain profile, make, model, vehicle order. No provider network call or worker runs within these transactions.

The staff branch-capability workspace is available from provider branch cards at `/staff/providers/{providerId}/branches/{branchId}/capabilities`. It includes canonical bilingual range entry, maker/checker review and actor-bound command recovery. Offer-revision fitment entry and saved review are available on the existing `/staff/offers/{offerId}` detail screen, after initial commercial draft creation. There is no booking/pass/payment, provider data import, engine/trim qualifier or launch-gate enablement. A future reservation must revalidate the exact current fitment and capability and snapshot pinned terms atomically; this backend does not imply that reservation is currently safe to take.

### Staff capability read projection

The authenticated capability collection GET adds `context`, `currentByCategory`, canonical bilingual labels/activity, action eligibility and decision/timing context to the existing policy fields. Policies and current pointers are read within one Repeatable Read transaction. Sales still sees only its own policy evidence and coverage. The current-pointer summary may identify another maker's current version, but includes no evidence, coverage or actor/contact details. Eligibility is a display hint only; mutation guards remain authoritative. Nested workspace URLs first resolve the branch through the authorized provider read and refuse mismatched parent/branch pairs.

The UI records only command identity, actor/resource/CAS metadata and a SHA-256 request fingerprint in tab-scoped session storage. Evidence, coverage and rejection text remain in memory, not the journal. A lost response is not proof of rollback. Recovery reads the original actor-bound receipt, separately refreshes current state, and permits only an identical same-key retry. After reload, content-bearing retries require deliberate exact re-entry and fingerprint equality; if the content cannot be reconstructed, staff must obtain operational assistance without clearing the unresolved journal. A historical approval receipt never reactivates a withdrawn or replaced version. Request deadlines stop waiting, not database execution.

This is an additive read/UI deployment with no new migrations or mutation semantics. Frontend rollback removes access to the screen, not recorded approvals or receipts. Existing follow-ups for bounded capability-history pagination, direct-SQL lock discipline and parser byte-cap test isolation remain separate.

### Staff offer-revision fitment entry and review (PR 4B-C2)

Offer fitment states which exact fixed scope, parts and price apply to a finite vehicle list. It is not the branch's category-scoped capability. Both supported modes require explicit evidence and bounded canonical make/model/year coverage; the service-independent mode does not mean unrestricted coverage. Neither mode asserts engine or trim support. An unassessed draft has no assumed verified mode.

The private fitment GET preserves its `{data: {revisionId, offerId, version, mode, evidenceRef, coverage}}` envelope and existing coverage IDs/years. Each coverage row additionally includes `make` and `model`, each limited to `{id, nameEn, nameAr, isActive}`. These labels come from the saved canonical relations, including inactive historical choices, not just the active catalogue. Additive `context` contains only current `providerStatus`, `branchStatus`, `serviceIsActive` and `categoryIsActive`, distinct from historical evidence and assessed coverage. Revision version, coverage, labels and dependency context are read in one bounded Repeatable Read transaction because Prisma may query included relations separately. Transaction-local PostgreSQL lock and statement deadlines are 3 and 7 seconds, with the existing 4-second acquisition and 8-second interactive transaction bounds. Names remain display labels, not frozen evidence or identity substitutions. The Sales ownership check and offer/revision parent guard remain authoritative; responses remain no-store.

Sales edits only its own draft. Commercial and fitment changes share the revision CAS version; a successful fitment save resets fitment attestations, increments that version and requires authoritative refresh before submission. The screen interlocks commercial editing, fitment editing and revision actions so dirty or pending/unknown work cannot be silently replaced or submitted. Distinct Operations review still requires all six explicit revision-bound checks. Approval is not publication or booking, and branch capability is not silently copied into offer evidence.

Fitment saves return a command receipt, not the updated revision. The original actor, offer/revision, expected version, command ID and request fingerprint identify recovery; evidence, mode and coverage bodies are not stored in the browser journal. After an ambiguous result, query the original actor-bound receipt and read current revision state separately. A receipt proves historical application only. Missing receipts do not prove rollback: any retry must retain the exact original body, key and version. After reload, deliberate exact re-entry must match the fingerprint; otherwise the command stays unresolved and requires approved operational assistance. A different account must not hydrate private original content or consume its receipt; return to the original authenticated workspace. Never clear recovery storage or issue a new command merely to bypass uncertainty.

No production mutation semantics, dependencies, schema or release gates change in this slice. Reverting the UI does not undo saved coverage, receipts or reviewed revisions. Real provider evidence must still be checked outside this application in the designated company-controlled repository; synthetic engineering fixtures do not satisfy that launch prerequisite.

`npm run test:integration` runs bootstrap-dependent CLI, authorization and staff-auth suites in explicit phases before the remaining shared disposable-database suites. Fitment tests retain immutable synthetic review history; they must not cause a later first-admin bootstrap test to depend on Vitest's estimated-duration scheduling. No immutable guards are disabled and no existing assertions are excluded: the general phase excludes only suites already executed explicitly.

Editor identity excludes the mutable CAS version so an authoritative refresh cannot erase dirty input by remounting the component; explicit discard or deliberate resource/account changes control resets, following React's [state preservation guidance](https://react.dev/learn/preserving-and-resetting-state). Review actions verify the actual session actor again before dispatch, invalidate stale checks on account changes, and reload before permitting fresh review. Recovery restores the journal's original revision even when a newer successor exists, and read-only commercial revisions retain reconciliation controls.

The client cleanup/generation guards follow React's [effect cleanup and stale-response guidance](https://react.dev/learn/synchronizing-with-effects#fetching-data). Permission hints do not replace the server-side DAL boundary described in the [Next.js authentication guide](https://nextjs.org/docs/app/guides/authentication#creating-a-data-access-layer-dal).
