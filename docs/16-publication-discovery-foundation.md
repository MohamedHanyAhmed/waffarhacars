# PR 4A: explicit publication and gated discovery

This is an internal foundation, **not a customer launch**. An approved offer revision is not public until an authorized Operations supervisor explicitly publishes that exact revision. There is no customer booking, vehicle-fit guarantee, reservation, payment, or provider self-service in this slice. The older showcase pages remain demo-only and are not a production fallback.

## Deployment controls

- `OFFER_PUBLICATION_ENABLED=false` is the default. Public list/detail returns an empty list/404 while disabled; publish and replace are unavailable. Operations can still withdraw and reconcile commands.
- `OFFER_PUBLICATION_PILOT_CLUSTER` has **no default**. It must be one of `NASR_CITY_HELIOPOLIS`, `NEW_CAIRO`, `MAADI`, or `OCTOBER_ZAYED`. Missing or malformed values fail closed for public reads and publish/replace, but do not prevent withdrawal.
- `OFFER_EVIDENCE_PACKET_REPOSITORY_READY=false` is an independent pre-existing business gate. It must be truthfully enabled only after Operations has repository access and packet retrieval/retention ownership is assigned. It gates publish/replace and public visibility.
- Even with these gates enabled for synthetic CI tests, production launch is prohibited until vehicle compatibility, the customer journey, merchant readiness and operational evidence controls have separate approval.

## Publication and withdrawal

Operations uses the authenticated `GET/POST /api/v1/staff/ops/offers/{offerId}/publication` endpoints. A POST carries a UUID `commandId`, `expectedVersion`, an action (`PUBLISH`, `REPLACE`, or `UNPUBLISH`), and a revision ID for publish/replace. The selected revision must belong to the offer, be approved with all four attestations, and remain otherwise eligible. Publication is independent of `Offer.currentApprovedRevisionId`: approving a later revision never silently changes public terms. `REPLACE` explicitly changes the pin; `UNPUBLISH` is the durable withdrawal. An already-published offer whose provider or branch is temporarily paused is effectively hidden; resuming the dependency can reveal the still-published offer again. Use `UNPUBLISH` for a permanent withdrawal.

The publication row, durable command outcome and sanitized security audit event commit in one transaction. The application writes an outcome once; this is not a cryptographically tamper-evident ledger. A replay with the same actor, identity and payload returns its recorded outcome without a second audit or version increment. A changed payload with the same identity conflicts. A terminal semantic rejection is recorded as a rejected command, not a publication mutation. A transient database/audit/lock failure rolls everything back; retry **only the same command identity** after checking `GET /api/v1/staff/ops/offers/{offerId}/publication/commands/{commandId}`. This reconciliation endpoint requires current Operations authorization and returns the original command outcome separately from current publication state. It never grants permission merely because the actor previously had it. In the Operations UI, a missing receipt leaves the original journal intact and reveals an explicit **Retry same publication command** control; it never silently generates a new key, changes the actor, target, or expected version, or claims that the first attempt rolled back. The original Operations account must be signed in to recover it. A recorded rejection clears the old journal and requires a new explicit decision. Reload the offer and recheck the command after an interrupted response; deleting browser storage is not a normal recovery procedure.

Publication transactions follow the existing lock order: provider → branch → offer → revision → service → category → publication. The offer row serializes competing first-publication commands. PostgreSQL lock waits are bounded. A request whose commit succeeded but response was lost is an unknown outcome, not a failure: preserve the resource-scoped command ID and reconcile before allowing another action. A 404 from reconciliation after a transient failure is not proof that an in-flight transaction can never commit. The explicit same-key retry is safe even if the first request remains in flight because both attempts serialize on the offer row and the durable receipt is replayed; a bounded lock timeout remains retryable with the same identity after another recheck. Withdrawal recovery remains available when the publication gate is disabled or a dependency becomes inactive.

## Anonymous discovery

`GET /api/v1/offers` and `GET /api/v1/offers/{offerId}` use the same database-level predicate at statement time. Only a published pinned revision that is approved, within its exact validity window, fixed-scope, attested, linked to an active matching service/category, and attached to an active vetted provider/branch in the configured pilot cluster is visible. Provider/branch pause, service/category deactivation, expiry, gate disable and unpublish hide it on the next read without a worker. Responses are dynamic and `no-store`; previously displayed pages cannot be recalled. Future reservations must independently revalidate eligibility and snapshot immutable terms.

The public DTO is an explicit allowlist of bilingual customer-facing terms, prices and vetted branch location/hours. Monetary values are integer-piastre strings; savings are derived from the pinned revision. It excludes internal identities, tax/registration data, commission, evidence packet IDs, notes, audit metadata, and branch phone (there is no explicit public-contact consent flag yet). Callers must render text as text, never executable HTML. Filters, page size and cursor are bounded; public database errors return sanitized 503, never demo data.

## Recovery and migration

The additive migration creates empty publication and command tables. It does not backfill or publish existing approved offers. Deploy forward; use a follow-up corrective migration for schema defects and database backup/PITR for disaster recovery. To contain an incident, turn off the deployment gate immediately and explicitly unpublish affected offers; the gate is a visibility control, not a substitute for durable withdrawal. Review sanitized command outcomes and audit events for reconciliation; do not log raw requests, credentials, SQL, PII or evidence references.
